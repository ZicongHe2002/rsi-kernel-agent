# Confirmation auxiliary drivers

These are task-owned host helpers, not a new execution system. `prepare_confirmation_round.py` validates a root-authored selection and prepares the original Analyzer session. `run_confirmation_round.py` accepts only a completed conversation response, then calls original publication, Intake and Controller.

`selection.json` has schema_version=1 and exact fields: task_id, context_id, strategy_id, candidate_id, baseline_candidate_id, round_id, previous_round_ids, knowledge, plan_roles, sequence. `previous_round_ids` is either the completed `real-runtime2-round:1` (the P3.5 window before round2) or the original ordered pair `real-runtime2-round:1`, `real-runtime2-round:2`; empty, unknown, and reordered histories are rejected. The saved selection remains immutable on recovery. `plan_roles` maps baseline/candidate to the two explicit proposal IDs. `sequence` has four role/label/priority objects in baseline,candidate,candidate,baseline order, unique labels and strictly descending priorities.

Both origins must have original confirmed five-stage receipts in the same context/strategy. The P3.5 readmission preserves this lineage check: the A repaired baseline remains A, while the delayed-store-wait treatment remains B. Independently remeasure the original B repaired-baseline Candidate in the new Context as `confirmation-control-runtime3-job.json`; `require_gates` may return that separately verified control for the confirmation origin lookup. The delayed treatment retains its `baseline-b-runtime3` gate identity for the following round. Do not relabel an A record as B or relax the strategy check. The helper pins existing source/config/build/bundle bytes, does not select a winner, and will reject altered artifacts in a replicate. New Candidate/Run IDs represent measurement replicas, not new optimization variants. Knowledge revisions and explicit selected parent are pinned on preparation. Every listed prior round must be terminal; current task must have no other unfinished jobs, at least four executions and 7200 declared seconds available, and original limits unchanged.

The original scheduler is simulated on a detached state before admission to check ABBA order. max_concurrency remains1. On restart, original operation/receipt/Controller budget owns recovery; completed operations are not rerun. Unknown stops the helper. No global dependency, Oracle, timer, benchmark protocol or promotion algorithm is changed.

Two independent Runs per implementation are limited replication. Report both baseline endpoints, both candidates, all raw samples, Profile and environment/lease/identity/input checks. Do not treat forty within-Run samples as forty independent experiments. Do not modify Store Best to agree with a statistical interpretation.

Tests were written before implementation and initially failed on missing modules. First implementation found the journal stores normalized limits including default weights; comparing raw LIMITS was wrong. The helper now compares validate_limits(LIMITS), without altering the original budget. Seven CPU/Synthetic tests cover original scheduler order, budget/pause rejection, immutable selection/session recovery, artifact substitution rejection, partial execution/restart, exact attempt IDs and no repeated spending. These tests do not prove real TPU repeatability.

P3.5 ordering compatibility was verified on 2026-11-13. Three added regressions failed against the original two-round requirement (3 failures, 119.664 seconds). After the allow-list change, `knowledge-site/.venv-mcp/Scripts/python.exe .artifacts/phase3-2026-11-12/test_confirmation_round.py -v` passed all 10 tests in 493.643 seconds. The added cases cover round1-only preparation, invalid prior-round lists, immutable saved prior-round selection, retained completed-round checks, and pinned participating-strategy history. The run used temporary Stores and Synthetic execution only; normal asyncio slow-task diagnostics were emitted. No production Store, remote bridge, TPU, Model API, budget limit, schema, or benchmark change was involved.
