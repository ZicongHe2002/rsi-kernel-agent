## 六、接下来的工作起点已经很明确

报告给出的恢复顺序总体合理。我会将后续讨论的起点固定为下面几个具体动作，而不是重新设计一套系统：

1. **核查 Runtime 4 与原 correctness operation。**
   最后一次看到 `running` 不代表现在仍在运行；本地缺回执也不能证明远端没有完成。先确定原请求的实际状态，再回收或推进。
2. **完成 Runtime 4 的原四项重新准入。**
   新环境中的错误负例和父版本结果核验通过后，再切换 active binding。同步探针返回 140.0 只说明当时探针成功，不能代替这些检查。
3. **读取包含中断归档和新准入结果的新 Snapshot，恢复第二轮。**
   旧 Runtime 3 的 ABBA 可以提供历史经验；新环境中的性能比较，应使用相应 Context 下重新测得的父版本。
4. **运行恢复候选与独立单 tile 诊断。**
   保持原正确性与计时契约，分别记录各候选的真实结果。
5. **回写并核对 Memory、Best、Frontier、Current Parent 和预算。**
   让第二轮的真实反馈进入系统，再判断 P3.5 各项 Gate 的完成情况。

报告中的剩余预算是 **6 次探索执行**，正好对应 **4 个恢复候选 + 2 个诊断 Run**，没有额外修复或新增独立复测的余量。这意味着恢复时尤其需要准确回收旧 operation，避免重复派发消耗预算。

下一次里程碑最有说服力的交付，会是一组完整的第二轮记录：**第一轮提供了什么依据，第二轮据此改了什么，真实 TPU 得到了什么结果，以及这些结果怎样改变 Memory 和后续探索。 同时如果第二轮ok的话，你就一直自己迭代，如果tpuv6-e分配不到，就一直申请不要停**
